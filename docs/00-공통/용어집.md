# 용어집 · 약어 · 참조표준 (DOC-00)

> 세 원본 문서의 용어를 통합·정규화한 **단일 기준(Single Source of Truth)**.
> 모든 문서(Tier A 사양 DOC-10·20, Tier B 참조 REF-01~03)는 본 문서의 표기를 따른다. 표기 흔들림이 곧 개념 혼선이므로,
> 새 용어를 도입할 때는 반드시 본 문서에 먼저 등록한다.

---

## 0. PKI 계층 및 검증 원칙 (가장 중요)

### 0.1 통합 CA 계층 구조

전 문서 공통의 단일 PKI 계층이다. FOTA(DOC-10)와 진단/클라우드(DOC-20)는 **같은 Root CA를 공유**하며,
목적별로 두 개의 중간 CA로 분기한다.

```
OEM Root CA  (최상위, 오프라인 보관 — 하위 CA 발급 시에만 사용)
├── Dev-IC  (Device CA, 디바이스 CA)
│     └─ 발급 대상: 제어기 신분 인증서(TGU·SGW·ECU '부품 정품 인증서'),
│                    진단툴 DMS '라이선스 인증서'
└── CS-IC  (Code Signing CA, 코드서명 CA)  [FOTA 전용]
      └─ 발급 대상: 'SW 개발자 인증서'
      └─ 역할: 배포 서명 생성 (배포 시스템 요청 시)
```

| CA | 정식 명칭 | 발급 대상 | 등장 문서 |
|----|-----------|-----------|-----------|
| Root CA | OEM Root Certificate Authority | Dev-IC, CS-IC (하위 중간 CA) | 전체 |
| **Dev-IC** | Device CA (디바이스 CA) | 제어기 부품 정품 인증서, DMS 라이선스 인증서 | DOC-10, DOC-20 |
| **CS-IC** | Code Signing CA (코드서명 CA) | SW 개발자 인증서, 배포 서명 | DOC-10 |

### 0.2 인증서 검증 원칙 — "발급 CA 공개키"

**어떤 인증서든, 그 인증서를 직접 발급(서명)한 CA의 공개키로 검증한다.** 검증 기준을 지칭할 때는
막연히 "Root CA 공개키"라 하지 않고 **"발급 CA 공개키"**로 정밀하게 표기한다.

| 검증 대상 인증서 | 발급 CA (=검증 기준) | 검증 주체 |
|------------------|----------------------|-----------|
| CS-IC 인증서 | **Root CA 공개키** | 인스톨러(TGU) |
| SW 개발자 인증서 | **CS-IC 공개키** | 타겟 제어기(HSM) |
| DMS 라이선스 인증서 | **Dev-IC 공개키** | SGW |
| 제어기 부품 정품 인증서 | **Dev-IC 공개키** | 상대 노드 / 클라우드 |

> 단일 계층(Root이 직접 발급)일 때만 "발급 CA 공개키 = Root CA 공개키"가 성립한다.
> 검증 기준이 되는 공개키만 내장하고 발급 CA 인증서를 함께 전달받아 **체인 검증**하는 방식도 가능하다.

## 1. 약어 (Abbreviations)

> *(확인 필요)*로 표시된 확장은 원본에 근거가 없는 **잠정 표기**이므로 대외 배포 전 사내 확정한다.

| 약어 | 원어 | 설명 |
|------|------|------|
| FOTA | Firmware Over-The-Air | 무선 펌웨어 업데이트 |
| PKI | Public Key Infrastructure | 공개키 기반 구조 |
| CA | Certificate Authority | 인증기관 |
| Root CA | Root Certificate Authority | 최상위 인증기관 (오프라인 보관) |
| Dev-IC | Device (Intermediate) CA | 디바이스 CA — 기기·진단툴 인증서 발급 (§0.1) |
| CS-IC | Code Signing (Intermediate) CA | 코드서명 CA — 개발자 인증서·배포 서명 (§0.1) |
| HSM | Hardware Security Module | 하드웨어 보안 모듈 |
| KMS | Key Management System | 키 관리 시스템 — 운영 KMS(온라인)는 Dev-IC/CS-IC 개인키·FW-Group-Key 보관, **CA만 접근**. Root 개인키는 별도 에어갭 오프라인 HSM (§2 참조) |
| CSR | Certificate Signing Request | 인증서 서명 요청 |
| UDS | Unified Diagnostic Services | 통합 진단 서비스 (ISO 14229) |
| SGW | Secure Gateway | 보안 게이트웨이 (내부 방화벽, 오프라인 검증 앵커) |
| TGU | Telematics Gateway Unit | 텔레매틱스 게이트웨이 — **이중 역할** (§2 참조) |
| ECU | Electronic Control Unit | 전자 제어기 |
| EPOS | Electric Power Optimization System | 건설기계 메인 유압 제어기 (FOTA 타겟 제어기 예시) |
| eSync | eSync (OTA Alliance 표준) | OTA 배포 캠페인 관리 표준 — **미도입, CRA 대응 유력 솔루션으로 검토 중** (§2 참조) |
| MES | Manufacturing Execution System | 제조 실행 시스템 (레거시) |
| ERP | Enterprise Resource Planning | 전사 자원 관리 (레거시) |
| FMS | Fleet Management System | 차량군 관리 시스템. 디지털키 도메인에서는 FMS 앱이 디지털키 기능을 통합한 사용자 클라이언트다(발급은 디지털키 시스템이 수행 → DOC-50) |
| VLM | Vehicle Lifecycle Management | 차량 생애주기 관리 — **미도입·개념적 추상 존재** (§2 참조) |
| DMS | Diagnostic Monitoring System | 장비 진단 시스템 |
| EOL | End-Of-Line | 완성차 조립 최종 공정 |
| JITP | Just-In-Time Provisioning | 최초 접속 시점 프로비저닝 (AWS IoT) |
| mTLS | mutual TLS | 상호 TLS 인증 |
| KEK | Key-Encryption Key | 키 암호화 키 — 다른 키를 암호화(랩핑)하는 키. 예: `FW-Group-Key` |
| DEK | Data-Encryption Key | 데이터 암호화 키 — 실제 데이터(펌웨어)를 암호화하는 키. 예: `AES-TSK` |
| TSK | Temporary Session Key | 임시 세션 키 — 배포 1회용 펌웨어 대칭 암호화 키(=DEK, AES). KEK인 FW-Group-Key로 랩핑됨 |
| ARVN | Anti-Rollback Version Number | 롤백 방지 보안 버전 번호 (§3 참조) |
| SBOM | Software Bill of Materials | 소프트웨어 구성 명세 |
| CRA | Cyber Resilience Act | EU 사이버 복원력 법안 |
| CCC | Car Connectivity Consortium | 디지털키(Digital Key) 표준 제정 단체·표준 (§5·DOC-50) |
| BLE | Bluetooth Low Energy | 저전력 블루투스 (디지털키 통신, TGU 내 MCU 담당) |
| SecOC | Secure Onboard Communication | 차량 내부 통신 보안 (AUTOSAR) |
| P&P | Plug & Play | 부품 자가 교체 즉시 통신 허용 |

## 2. 노드(주체) 정의 — 역할 고정

| 구역 | 노드 | 역할 | 비고 |
|------|------|------|------|
| **OEM 백엔드(격리)** | **KMS** | 키관리·격리 공간. 운영 KMS(온라인)=Dev-IC/CS-IC 개인키·FW-Group-Key. Root 개인키=별도 에어갭 오프라인 HSM | **CA만 접근 가능** |
| **OEM 백엔드(격리)** | **CA 계층** | Root CA(오프라인) → Dev-IC(디바이스 CA) + CS-IC(코드서명 CA) | KMS의 유일 접근자 (→ [DOC-10 §1](../10-시스템장비-보안아키텍처/시스템장비-보안아키텍처명세서.md)) |
| **클라우드** | **배포 시스템** | 자체 OTA Platform — FW 패키징·아티팩트·배포 캠페인 | 개인키 미보유(배포 서명은 CS-IC에 **요청**). **eSync 전환 계획**. '배포 서버'는 전달 엔드포인트 |
| **클라우드** | **AWS IoT Core** | **연결점**(mTLS·JITP). 캠페인·배포는 안 함 | **Dev-IC와 별개이나 관련** — JITP용 Dev-IC/Root CA 인증서 등록처 (아래 주석) |
| **클라우드** | VLM (차량 레지스트리) | 식별자↔VIN 매핑·SBOM 이력 | **미도입·개념적 추상** (아래 주석) |
| **장비(OT)** | **TGU** | ① **인스톨러**(배포 서명 검증·라우팅, DOC-20) ② **텔레매틱스**(AWS 접점·mTLS, DOC-10/40) | 동일 장비 두 역할. Tier 1. **유일 클라우드 출구** |
| **장비(OT)** | **SGW** | 내부 방화벽·오프라인 검증 앵커 (UDS 0x29 게이트) | 자기 증명 불필요, 타인 검증만. Tier 2 |
| **장비(OT)** | 제어기(ECU) | 차상 제어기. **HSM 보유(예: EPOS) / 비-HSM**으로 구분 | 'FOTA 타겟'은 노드 유형이 아니라 **역할**(§3 참조) |
| **현장** | DMS | 정비사 진단툴(SW). 라이선스 인증서로 권한 증명 | Windows PC |

> **[미도입 시스템 · 설계 취급]**
> - **VLM:** 아직 당사 미도입. 레거시(MES/ERP/FMS) 통합 / Dev-IC·KMS 통합 / 독립 구축 중 배치가 미정이므로, 본 문서에서는 **역할(식별자↔VIN 매핑, 생애주기·SBOM 이력)만 갖는 개념적 추상 존재**로 정의한다. 문서 고도화 단계에서 실체를 구체화한다.
> - **배포 시스템 / eSync:** FW 캠페인·배포는 **자체 OTA Platform(=배포 시스템)**이 수행하며, AWS IoT Core가 아니다. 현재 자체 OTA Platform이나 **향후 eSync로 전환할 계획**이므로, 패키지·캠페인 구조를 eSync 호환으로 지향한다(전환 시 변경 최소화). → DOC-20.
> - **AWS IoT Core:** 클라우드 **연결점**(mTLS·JITP). 캠페인·배포는 수행하지 않는다. **Dev-IC와 별개 객체이나 관련** — JITP가 디바이스 인증서 체인을 검증하려면 **Dev-IC(및 Root) CA 인증서를 AWS IoT Core에 등록**해야 한다. TGU만 접속한다.

## 3. 핵심 용어

| 용어 | 정의 |
|------|------|
| 배포 서명 (Distribution Signature) | CS-IC가 서명(배포 서버 요청 시), 인스톨러(TGU)가 검증하는 외부(Outer) 서명 |
| 펌웨어 서명 (Firmware Signature) | SW 개발자/벤더가 부착, 타겟 제어기(HSM)가 검증하는 내부(Inner) 서명 |
| 이중 전자서명 (Dual Signature) | 배포 계층 + 설치 계층으로 분리된 2단 서명 구조 |
| FW-Group-Key | 펌웨어 기밀성용 대칭 **KEK**(Key-Encryption-Key). 일회용 `AES-TSK`(DEK)를 랩핑하며, HSM에 인증서 확장 필드로 주입. **그룹 단위는 정책**(현재 기종별, 후보 품번별). 무결성은 서명이 담당하므로 유출 위험은 IP 열람에 국한 (→ DOC-10 §1.3) |
| AES-TSK | 배포 시마다 생성되는 일회용 대칭키(DEK). FW-Group-Key(KEK)로 랩핑됨 |
| Secure Flash | 대칭키(FW-Group-Key) 기반 펌웨어 기밀성 보호(암호화 배포) |
| Secure Boot | 부팅 시 활성 뱅크 무결성을 HSM으로 재검증하는 절차 |
| **ARVN (버전 번호)** | 패키지 매니페스트·펌웨어 헤더에 **기재된** 보안 버전 번호 (데이터) |
| **HSM 롤백 카운터** | ARVN과 대조하는 HSM 내부의 **단조증가 비휘발성 카운터** (하드웨어). ARVN과 별개 객체 |
| Anti-Rollback | ARVN을 HSM 롤백 카운터와 대조하여 구버전 다운그레이드를 차단하는 메커니즘 |
| Chain of Trust | 발급 CA 공개키로 인증서를 검증하고, 검증된 인증서의 공개키로 다음 단계를 검증하는 신뢰 연쇄 (§0.2) |
| 활성 뱅크 (Active Bank) | A/B 뱅크 중 현재 실행 중인 펌웨어 저장 구역 |
| Challenge-Response | UDS 0x29 난수 서명 기반 상호 인증 |
| 제어기(ECU) | 차상의 전자 제어기 통칭(TGU·SGW 포함). **HSM 보유/비-HSM**으로 구분 |
| 타겟 제어기 | **역할** — FW 업데이트 설치·Secure Boot 대상 제어기(HSM 보유). 노드 유형이 아님 (예: EPOS) |
| 부품 정품 인증서 | Dev-IC가 제어기(TGU·SGW)에 발급하는 신분 인증서. TGU는 동일 인증서를 로컬(.der)·클라우드(.pem) 두 인코딩으로 사용 |
| 디지털키 (Digital Key) | 장비 물리 접근·조작 인가를 위한 CCC 기반 키. **코어 PKI와 별도 도메인**, 자체 암호 스위트(Ed25519 등 — 확인 필요). 디지털키 시스템이 발급하고 사용자 FMS 앱이 보유한다 (DOC-50) |
| 모바일앱 (FMS 앱) | 디지털키 기능이 통합된 사용자 앱. 사용자 디지털키를 보유하고 장비(TGU BLE)와 보안 통신 (DOC-50) |
| DMS 라이선스 인증서 | Dev-IC가 DMS PC에 발급하는 단기 인증서 (Role OID 포함) |

## 6. 참조 표준 (초안 — 확정 필요)

- ISO 14229 (UDS), ISO 14229-1 §0x29 Authentication
- ISO 21434 (도로차량 사이버보안 엔지니어링)
- UNECE R155 / R156 (사이버보안 / SW 업데이트 관리)
