# term-guard — 용어 가드

이 프로젝트는 세 개의 서로 다른 원본에서 출발했고, 같은 개념을 다르게 부르던 흔적이 남아 있다.
용어가 흔들리면 독자가 개념을 오해한다. **[docs/00-공통/용어집.md](../../../docs/00-공통/용어집.md)(DOC-00)가
유일한 기준**이며, 이 스킬은 문서를 쓰거나 고칠 때 그 기준을 지키게 한다.

## 작업 순서

1. **쓰기 전 확인:** PKI/FOTA/UDS 용어를 쓰려 하면 먼저 DOC-00에 등록된 표준형인지 확인한다.
2. **표준형으로 교정:** 아래 금지형↔표준형 표에 걸리면 표준형으로 바꾼다.
3. **새 용어면 등록부터:** DOC-00에 없는 용어를 도입하려면, 본문에 쓰기 전에 DOC-00에 먼저 등록한다
   (약어표/핵심 용어/노드 정의 중 맞는 곳). 근거가 없으면 확장을 지어내지 말고 `(확인 필요)`로 표시한다.
4. **미확정은 표시:** 아직 안 정해진 값은 `TODO`/`TBD`로 남기고 DOC-00 §5 추적표에 반영한다.

## 표준형 (금지형 → 표준형)

이유를 함께 적는다. 규칙을 외우기보다 왜 그런지 이해하면 새로운 상황에도 적용할 수 있다.

| 쓰지 말 것 | 표준형 | 이유 |
|-----------|--------|------|
| 통합 디바이스 CA | **디바이스 CA(Dev-IC)** | DOC-20의 '통합 디바이스 CA'와 DOC-10의 'Dev-IC'는 동일 주체. 하나로 부른다 |
| (막연한) Root CA 공개키 / CA 공개키 | **발급 CA 공개키** | 인증서는 *직접 발급한 CA*의 공개키로 검증. 단일 계층일 때만 발급 CA = Root |
| Anti-Rollback Counter (패키지에) | **ARVN(롤백 방지 버전 번호)** | 패키지에 *기재된 버전 번호*와 HSM의 *단조 카운터*는 별개 객체 |
| (HSM 쪽) 버전 번호 | **HSM 롤백 카운터** | 위와 같은 이유. 하드웨어 단조증가 카운터 |
| Data Monitoring System | **Diagnostic Monitoring System (DMS)** | 진단 시스템으로 진화, 약어 DMS 유지 |
| Secure Flash 2.0 | **Secure Flash** | 정규화됨. "2.0" 버전 의미는 확인 필요(§5) |

## 검증 잣대 — 대상별 발급 CA (DOC-00 §0.2)

검증 잣대를 쓸 때는 "발급 CA 공개키"라고만 하지 말고 어떤 CA인지 특정한다.

| 검증 대상 | 발급 CA(=잣대) | 검증 주체 |
|-----------|----------------|-----------|
| CS-IC 인증서 | Root CA 공개키 | 인스톨러(TGU) |
| SW 개발자 인증서 | CS-IC 공개키 | 타겟 제어기(HSM) |
| DMS 라이선스 인증서 | Dev-IC 공개키 | SGW |
| 제어기 부품 정품 인증서 | Dev-IC 공개키 | 상대 노드/클라우드 |

## 확정된 약어 (지어내지 말 것)

EPOS = Electric Power Optimization System(메인 유압 제어기) · DMS = Diagnostic Monitoring System ·
VLM = Vehicle Lifecycle Management(**미도입·개념적 추상**) · eSync = OTA Alliance 표준(**미도입·호환 지향**).
FMS/ERP/MES는 레거시 시스템. 전체 목록·정의는 DOC-00 §1을 본다.

## 하지 말 것

- DOC-00에 근거 없는 약어 확장을 **사실처럼** 쓰기 → `(확인 필요)`로.
- 같은 개념을 문장마다 다르게 부르기 → 첫 등장 시 표준형(풀어쓰기+약어), 이후 일관 사용.
- 미도입 시스템(VLM/eSync)을 이미 존재하는 것처럼 단정 → "미도입/추상/호환 지향" 톤 유지.

## 애매하면

DOC-00에서 판단이 안 서면 지어내지 말고 사용자에게 확인하거나 `TBD`로 남긴다. 잘못 굳은 용어를
되돌리는 비용이 확인 비용보다 훨씬 크다.
