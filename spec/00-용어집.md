# 용어집 (eSync ↔ 우리 시스템 대응)

각 사양서([10 PKI](10-PKI-사양서.md) · [20 프로비저닝](20-프로비저닝-사양서.md) · [30 eSync OTA 공통 아키텍처](30-eSync-OTA-공통아키텍처.md) · [31 EPOS-10i](31-EPOS-10i-OTA사양서.md) · [32 EPOS-30i](32-EPOS-30i-업데이트-사양서.md) · [40 유선업데이트](40-유선업데이트-사양서.md)) 본문은 표준 스택인 **eSync**의 용어를 그대로 쓴다. 이 문서는 그 용어가 무엇을 뜻하는지, 그리고 우리 시스템의 어떤 구성요소에 대응하는지를 정리한다.

## 읽는 법

- 표제어는 eSync 용어이며, 그 아래 **우리 용어**로 대응 관계를 밝힌다.
- 각 항목은 하나의 위키 문서처럼 자기완결로 읽히도록 썼다. 해당 분야가 아니어도 이해할 수 있게 배경을 함께 설명한다.
- 항목 사이의 참조는 `[[표제어]]`로 잇는다.
- 자주 나오는 배경 개념을 먼저 정리한다.
  - **OTA(Over-The-Air)** — 장비를 정비소에 들이지 않고 무선망으로 소프트웨어를 갱신하는 방식.
  - **PKI(Public Key Infrastructure, 공개키 기반구조)** — 인증서로 신원과 서명을 증명하는 체계. 최상위 인증기관을 정점으로 하위 인증기관·최종 인증서가 계층(체인)을 이룬다. 상위의 서명을 차례로 따라가 신뢰를 확인한다.
  - **인증서(certificate)** — 공개키와 그 소유자 정보를 인증기관이 서명해 묶은 전자 신분증. 표준은 X.509.
  - **개인키/공개키** — 짝을 이루는 두 키. 개인키로 서명하면 공개키로 검증한다. 개인키는 소유자만 보관한다.
  - **mTLS(mutual TLS, 상호 인증 TLS)** — 서버와 클라이언트가 서로 상대의 인증서를 확인하는 암호화 연결.
  - **제어기(ECU)** — 장비에 탑재된 소프트웨어 제어 장치. 이 문서에서 갱신 대상이 되는 노드.

## 클라우드·백엔드 시스템

배포를 지시하고, 소프트웨어를 보관·서명하며, 장비와 통신하는 서버군이다.

### eSync Server

- **우리 용어:** 배포 플랫폼 (자체 OTA Platform)
- 업데이트를 어느 장비에 언제 배포할지 정하고(캠페인·타겟팅), 소프트웨어 구성요소와 패키지를 보관하며, 배포 이력을 남기는 클라우드 백엔드다. 인증서를 발급하는 인증기관은 **아니다**. 소프트웨어를 내보낼 때는 [[CS Cert]]의 개인키로 서명하는 **서명자**로, 장비가 접속할 때는 장비 인증서가 유효한지 확인하는 **검증자**로 동작한다.
- **관련:** [[eSync Client]] · [[Operator UI]] · [[GPDM]] · [[KMS]]

### eSync Client

- **우리 용어:** TGU (인스톨러)
- 장비 쪽 게이트웨이 노드다. 클라우드와 **mTLS**로 통신하며, 내려받은 업데이트를 장비 안의 여러 제어기에 설치하도록 지휘(오케스트레이션)한다. 장비에서 클라우드로 나가는 단일 창구 역할을 한다.
- **관련:** [[eSync Agent]] · [[eSync Server]]

### eSync Agent

- **우리 용어:** 업데이트 에이전트 (EPOS-10i의 경우 TGU에 동거)
- 실제 설치를 수행하는 구성요소로, 내려받은 소프트웨어의 서명을 검증하고 제어기 메모리에 기록(플래시)한다. EPOS-10i처럼 스스로 서명을 검증할 능력이 없는 제어기에서는, 게이트웨이(TGU)에 있는 eSync Agent가 검증을 대신 수행한 뒤 설치한다.
- **관련:** [[eSync Client]] · [[CS Cert]]

### Operator UI

- **우리 용어:** OTA 운영 플랫폼 (PS) · 운영 콘솔
- 캠페인·패키지·설치 현황을 사람이 조작하는 단일 화면이다. RBAC(Role-Based Access Control, 역할 기반 접근제어)로 권한을 나눠, 딜러·사후관리(AS) 담당자에게 필요한 기능만 부분 개방한다.
- **관련:** [[eSync Server]]

### GPDM

- **우리 용어:** HD현대건설기계 PLM
- 소프트웨어와 그 부품 목록(SW BOM, Bill of Materials)을 관리하는 제품 수명주기 관리(PLM, Product Lifecycle Management) 시스템이다. 배포될 소프트웨어의 원본이 시작되는 유일한 원장으로, GPDM에서 정식 릴리스된 산출물만 [[eSync Server]]로 넘어간다.
- **관련:** [[eSync Server]]

### KMS

- **우리 용어:** KMS (키 관리 시스템)
- 서명에 쓰는 개인키를 보관하는 시스템(Key Management System)이다. 개인키는 시스템 밖으로 나오지 않는다. [[eSync Server]]가 서명이 필요하면 대상 데이터를 KMS에 보내고, KMS 내부에서 서명한 결과만 돌려받는다. 키 자체를 노출하지 않으므로 유출 위험을 낮춘다.
- **관련:** [[CS Cert]] · [[eSync Server]]

### VLM

- **우리 용어:** VLM (차량 레지스트리)
- 장비의 시리얼 번호, 차대번호(VIN, Vehicle Identification Number), 장비 옵션 사이의 대응 관계와 소프트웨어 구성 이력(SBOM, Software Bill of Materials)을 관리하는 레지스트리다. 캠페인이 옵션별 [[SW 품번]] 변종을 정확히 겨냥할 때 판단 근거가 된다.
- **관련:** [[SW 품번]] · [[eSync Server]]

### AWS IoT Core

- **우리 용어:** AWS IoT Core (연결점)
- [[eSync Server]]와 장비(TGU)를 잇는 통신 접속점이다. TGU와 **mTLS**로 연결하고, 업데이트 지시 같은 신호(잡·MQTT 메시지)를 중계한다. 통신·전송 담당 팀 소관이다.
- **관련:** [[eSync Client]] · [[JITP]]

### JITP

- **우리 용어:** Just-In-Time Provisioning (최초 접속 등록)
- 장비(TGU)가 클라우드에 처음 접속하는 순간, [[AWS IoT Core]]가 그 장비의 사물(Thing)·인증서 정보를 계정에 자동 등록·활성화하는 절차다. 인증서를 새로 **발급**하는 것이 아니라([[디바이스 인증서]]는 Tier-1 공정에서 [[Device CA]]가 이미 발급함), 이미 있는 인증서를 클라우드에 **등록**하는 과정이다.
- **관련:** [[디바이스 인증서]] · [[VLM]]

## 인증기관(CA)과 신뢰 구조

누가 인증서를 발급하고, 그 신뢰가 어디서 출발하는지를 정하는 계층이다. CA는 Certificate Authority(인증기관)의 약자다.

### OEM Root CA

- **우리 용어:** OEM Root CA
- PKI 전체의 최상위 인증기관이다. 이 기관의 개인키는 인터넷과 분리해(오프라인) 보관하며, 오직 하위 인증기관을 발급할 때만 사용한다. 각 제어기에 심어 두는 신뢰의 출발점([[신뢰앵커]])이 여기서 나온다 — 이 앵커는 공개키가 아니라 Root CA 인증서로 배포한다. 아래의 [[Device CA]]·[[Code Sign CA]]·[[진단 라이선스 CA]]가 모두 이 기관의 자식이다.
- **관련:** [[Device CA]] · [[Code Sign CA]] · [[진단 라이선스 CA]]

### Device CA

- **우리 용어:** Dev-IC (디바이스 CA)
- 장비 신원 증명서, 곧 [[디바이스 인증서]]를 발급하는 인증기관이다. [[OEM Root CA]]의 하위에 있으며, 개인키는 [[KMS]]에 보관한다.
- **관련:** [[디바이스 인증서]] · [[OEM Root CA]]

### Code Sign CA

- **우리 용어:** CS-IC (코드서명 CA)
- 소프트웨어에 서명할 자격을 증명하는 [[CS Cert]]를 발급하는 인증기관이다. [[OEM Root CA]]의 하위에 있으며, 개인키는 [[KMS]]에 보관한다.
- **관련:** [[CS Cert]] · [[OEM Root CA]]

### 진단 라이선스 CA

- **우리 용어:** 진단 라이선스 CA
- 유선 진단툴([[DMS]])에 발급하는 [[DMS 라이선스]]를 담당하는 인증기관이다. [[OEM Root CA]] 아래에서 [[Device CA]]·[[Code Sign CA]]와 나란히 서는 형제 기관이며, 개인키는 [[KMS]]에 보관한다.
- **관련:** [[OEM Root CA]] · [[DMS 라이선스]]

### 신뢰앵커

- **우리 용어:** Trust Anchor (신뢰앵커)
- 인증서 체인 검증의 출발점이 되는 최상위 신뢰다. **공개키만이 아니라 자기서명 CA 인증서로** 보유한다 — 경로 검증에는 앵커의 이름(DN)·제약(용도·CA 여부)이 필요하기 때문이다(RFC 5280). 디바이스는 목적별로 여러 앵커를 갖는다: 자체 PKI 검증엔 [[OEM Root CA]] 인증서, AWS 전송 검증엔 [[Amazon Root CA]] 인증서.
- **관련:** [[OEM Root CA]] · [[Amazon Root CA]]

### Amazon Root CA

- **우리 용어:** Amazon Root CA (Amazon Trust Services)
- AWS가 운영하는 공개 루트 인증기관이다. TGU가 [[AWS IoT Core]] 엔드포인트에 [[mTLS]]로 접속할 때 **서버(엔드포인트) 인증서를 검증하는 신뢰앵커**로 쓴다. 우리 [[OEM Root CA]](자체 PKI)와는 별개이며, TGU는 둘 다 인증서로 보유한다. 코드서명·[[eSync Server]] 검증은 OEM Root CA로, AWS 엔드포인트 검증은 Amazon Root CA로 한다.
- **관련:** [[AWS IoT Core]] · [[신뢰앵커]] · [[OEM Root CA]]

## 인증서

앞의 인증기관이 발급하는 최종 신분증들이다. 각각 증명하는 대상이 다르다.

### CS Cert

- **우리 용어:** 코드서명 리프 인증서
- [[Code Sign CA]]가 발급한 최종(리프, leaf) 인증서로, "이 키로 서명한 소프트웨어는 정품"임을 보증한다. 용도가 코드서명으로 한정된다(`EKU=codeSigning`, EKU는 Extended Key Usage). 짝이 되는 개인키는 [[KMS]]에 두고 소프트웨어 구성요소에 서명하며, 장비가 그 서명을 검증할 수 있도록 인증서 자체는 구성요소에 함께 실어 보낸다. 유출 피해를 줄이기 위해 수명이 짧고 주기적으로 교체(회전)한다.
- **관련:** [[Code Sign CA]] · [[eSync Server]]

### 디바이스 인증서

- **우리 용어:** 부품 정품 인증서
- [[Device CA]]가 발급한 최종 인증서로, 장비(제어기)의 신원을 증명한다. 시리얼 번호를 이름으로 담는다(`CN=Serial`, CN은 Common Name). **mTLS** 접속에서 [[eSync Client]]가 자신이 정품 장비임을 입증하는 데 쓴다. 부품 공정(Tier-1)에서 발급되며, 짝이 되는 개인키는 제어기 안에만 보관한다.
- **관련:** [[Device CA]] · [[eSync Client]]

### DMS 라이선스

- **우리 용어:** DMS 라이선스 인증서
- 유선 진단툴([[DMS]])에 발급하는 짧은 수명의 X.509 인증서다. 발급받은 PC의 고유 식별자와 조작자 인증을 근거로 만들며, 그 사람이 어떤 작업을 할 수 있는지를 역할 식별자(Role OID)로 담는다. 같은 인증서 하나를, 게이트웨이([[SGW]])는 [[UDS 0x29 APCE]]로, 게이트웨이 노드([[eSync Client]])는 **mTLS**로 각각 검증한다.
- **관련:** [[진단 라이선스 CA]] · [[DMS]]

## 소프트웨어 구성요소·데이터

배포되는 소프트웨어 꾸러미와 그 안에 담기는 메타데이터다.

### Component / Package

- **우리 용어:** 컴포넌트 / 패키지
- **Component(컴포넌트)** 는 특정 대상 노드(`nodeName`)에 설치되는, 버전이 매겨진 소프트웨어 단위다(`name`·`type`·`versions` 등을 가지며, 바이너리 무결성은 `deltaSha`에 SHA-256 해시로 기록). **Package(패키지)** 는 함께 배포해야 하는 컴포넌트들을 묶은 꾸러미다(`components`·`componentRules`, 그리고 하나라도 실패하면 전부 되돌리는 `atomicRollback`). 캠페인은 이 패키지 단위로 배포한다.
- **관련:** [[manifest.xml]] · [[Signed Component Database]]

### manifest.xml

- **우리 용어:** 설치 매니페스트
- 컴포넌트(ZIP) 안에 들어가는 메타데이터 파일이다. 설치 대상 노드, 종류(type), 버전, 되돌리기(rollback) 가능 여부, 차분 갱신(delta) 정보, [[SW 품번]], [[호환성 정보 (HW)]] 등을 담는다. 컴포넌트 전체에 서명하므로, 이 매니페스트의 내용도 그 서명으로 함께 보증된다.
- **관련:** [[Component / Package]] · [[호환성 정보 (HW)]] · [[SW 품번]]

### Signed Component Database

- **우리 용어:** 서명된 컴포넌트 저장소
- [[eSync Server]]가 서명을 마친 컴포넌트를 보관하는 저장소다. 배포는 여기 담긴, 이미 서명된 산출물에서 나간다.
- **관련:** [[Component / Package]]

### 델타

- **우리 용어:** Delta 업데이트
- 소프트웨어 전체가 아니라 기준 버전과 달라진 부분만 전송하는 갱신 방식이다. 전송량과 시간을 줄인다. 차분 정보(`manifest_diff.xml`)와 기준 버전 참조를 함께 보내면, [[eSync Agent]]가 기준 버전에 차분을 더해 완성 이미지를 재구성한다.
- **관련:** [[manifest.xml]] · [[Component / Package]]

### SW 품번

- **우리 용어:** SW 품번 (Part Number)
- 장비 옵션별 소프트웨어 변종을 구별하는 **식별자**다. [[manifest.xml]]에 담기지만, 이것으로 설치 가능 여부를 판정하지는 않는다(그 판정은 [[호환성 정보 (HW)]]가 맡는다). 어느 장비에 어느 품번을 적용할지는 [[VLM]]과 정책으로 정하며, 장비가 스스로 골라 맞추지 않는다.
- **관련:** [[VLM]] · [[호환성 정보 (HW)]]

### 호환성 정보 (HW)

- **우리 용어:** HW 호환성 (HW 모델·버전)
- 해당 펌웨어를 설치할 수 있는 하드웨어 형상(모델·버전)을 명시한 정보다. [[manifest.xml]]에 담기며, [[eSync Agent]]가 진단 명령(UDS `0x22`)으로 제어기에서 실제 하드웨어 값을 읽어 이 명시값과 대조해 설치 가능 여부를 판정한다.
- **관련:** [[manifest.xml]] · [[SW 품번]]

## 진단·유선 경로

무선(OTA)이 아니라 정비 현장에서 케이블로 장비에 접속하는 경로와, 그 통신에 쓰는 진단 규약이다.

### DMS

- **우리 용어:** DMS (Diagnostic Monitoring System)
- 장비를 진단하고 소프트웨어를 유선으로 설치하는 Windows용 PC 프로그램(C#)이다. 장비에 상주하는 [[eSync Client]]·[[eSync Agent]]가 없는 대신, 서명과 호환성을 스스로 검증한 뒤 [[OBD-II]] 단자로 직접 설치하는 **유선 설치자**다(역할은 TGU와 유사). 설치할 서명 컴포넌트·패키지는 [[eSync Server]]/대시보드에서 내려받는다.
- **관련:** [[DMS 라이선스]] · [[SGW]] · [[OBD-II]]

### SGW

- **우리 용어:** SGW (Secure Gateway)
- 장비 안에서 외부 진단 단자([[OBD-II]]) 쪽 CAN 통신을 내부망과 분리·보호하는 보안 게이트웨이다. 자체 보안 연산 장치(HSM, Hardware Security Module)를 갖는다. 유선 진단툴이 접속하면 그 [[DMS 라이선스]]를 [[UDS 0x29 APCE]]로 검증하고, 통과한 경우에만 특정 CAN 선로를 개방한다. 신원·신뢰앵커를 미리 주입해 두는 프로비저닝 대상이다.
- **관련:** [[DMS]] · [[UDS 0x29 APCE]]

### OBD-II

- **우리 용어:** OBD-II
- 장비 외부에 노출된 표준 진단 접속 단자다. CAN([[SGW]] 경유)과 이더넷([[eSync Client]] 경유) 두 경로의 접속을 제공한다.
- **관련:** [[SGW]] · [[DMS]]

### UDS 서비스

- **우리 용어:** UDS on CAN (ISO 14229)
- 제어기를 진단·정비하기 위한 표준 통신 규약(UDS, Unified Diagnostic Services)이다. 서비스는 기능별 번호로 구분한다. `0x22`(ReadDataByIdentifier — 하드웨어 ID 조회), `0x27`(SecurityAccess — 시드·키 교환으로 플래시 세션을 여는 관문), `0x34`/`0x36`/`0x37`(RequestDownload/TransferData/RequestTransferExit — 플래시 데이터 전송), `0x29`(Authentication — 인증서 기반 인증, [[SGW]]가 [[DMS 라이선스]] 검증에 사용). `0x29`는 암호 연산이 불가능한 [[EPOS-10i]]에는 쓰지 않고, [[HSM]]을 보유한 [[EPOS-30i]]가 [[Secure Flash]] 세션 관문으로 쓴다.
- **관련:** [[eSync Agent]] · [[UDS 0x29 APCE]]

### UDS 0x29 APCE

- **우리 용어:** UDS Authentication (APCE)
- [[UDS 서비스]] 중 `0x29`(Authentication)의 인증서 기반(PKI) 방식이다(ISO 14229:2020). APCE는 그 인증 흐름의 명칭이다. 순서는 인증서 제시 → 체인 검증 → 서버가 보낸 도전값(challenge)에 개인키로 서명 → 개인키 소유 증명 → 역할(role) 기반 권한 부여로 이어진다. [[SGW]]가 유선 진단툴([[DMS]])을 검증하는 방식이다.
- **관련:** [[SGW]] · [[DMS 라이선스]]

### DoIP

- **우리 용어:** DoIP (ISO 13400)
- 진단 통신(UDS)을 이더넷·IP망 위로 실어 나르는 전송 표준(Diagnostics over IP)이다. 진단 메시지가 흐르기 전에 게이트웨이가 접속을 통제하는 [[routing activation]]과 논리주소 라우팅을 제공하지만, 인증 자체는 상위 계층에 맡긴다. TGU는 DoIP를 쓰지 않으므로, 접근제어를 **mTLS**로 대신한다.
- **관련:** [[eSync Client]]

### routing activation

- **우리 용어:** 라우팅 활성화
- [[DoIP]]에서 진단 메시지가 오가기 전에, 게이트웨이가 접속한 클라이언트의 자격을 확인하고 내부 경로를 열어 주는 관문 절차다. DoIP를 쓰지 않는 TGU는 이 역할을 **mTLS**와 역할 기반 접근제어로 대체한다.
- **관련:** [[DoIP]]

## 정책·운영 개념

설치 시점·복구·시각처럼 절차를 통제하는 개념들이다.

### Insurance Kernel

- **우리 용어:** 복구 부트로더
- 제어기의 보호된 메모리 영역에 상주하는 최소한의 복구 코드다. 플래시 도중 문제가 생겨 애플리케이션이 손상되더라도, 이 코드가 남아 있어 다시 플래시해 장비를 되살릴 수 있다. 메모리 뱅크가 하나뿐이라 안전한 예비 영역이 없는(싱글뱅크) 제어기의 복구 수단이다.
- **관련:** [[eSync Agent]]

### 설치 정책

- **우리 용어:** InstallationPolicy
- 업데이트를 언제·어떤 조건에서 설치할지 통제하는 규칙이다. 시동이 꺼진 상태(`ignition_off`), 네트워크 상태, 허용 시간대 같은 조건을 지정해, 안전하지 않은 시점의 설치를 막는다.
- **관련:** [[eSync Client]]

### 신뢰 시각

- **우리 용어:** Trusted Time
- 인증서 유효기간이나 폐기 여부(OCSP) 확인처럼, 신뢰할 수 있는 현재 시각을 필요로 하는 검증에 쓰는 시각원이다. 장비가 임의로 조작할 수 없는 믿을 만한 출처를 TGU가 확보해야 한다.
- **관련:** [[디바이스 인증서]]

## 제어기·HSM 보안 (EPOS 계열)

HSM을 보유한 제어기가 스스로 서명 검증·복호화·보안 부팅을 수행할 때 쓰는 개념들이다.

### EPOS-10i

- **우리 용어:** EPOS-10i (유압 제어기, 현세대)
- HSM이 없어 서명 검증·암복호화를 스스로 못 하고, 메모리 뱅크가 하나(싱글뱅크)이며 UDS `0x29`를 지원하지 않는 제어기다. 무결성 검증을 [[eSync Agent]](TGU)가 대행하고, 평문으로 플래시하며, `0x27`로 세션을 보호한다. 상세는 [31 EPOS-10i](31-EPOS-10i-OTA사양서.md).
- **관련:** [[eSync Agent]] · [[Insurance Kernel]] · [[EPOS-30i]]

### EPOS-30i

- **우리 용어:** EPOS-30i (유압 제어기, 차세대·CRA 대응)
- EPOS-10i를 CRA에 대응해 업그레이드한 제어기로, [[HSM]]과 [[A/B Dual Bank]]를 갖춘다. 서명 검증·복호화를 **제어기 자체가** 수행하고, 암호화 페이로드([[Secure Flash]])를 받으며, UDS `0x29`로 세션을 보호한다. 상세는 [32 EPOS-30i](32-EPOS-30i-업데이트-사양서.md).
- **관련:** [[HSM]] · [[Secure Boot]] · [[Secure Flash]] · [[A/B Dual Bank]]

### HSM

- **우리 용어:** HSM (Hardware Security Module)
- 제어기 안에서 키를 보관하고 암호 연산(서명 검증·복호화·MAC)을 전담하는 하드웨어 보안 모듈이다. EPOS-30i는 AURIX TC387QP의 HSM 코어(Cortex-M3)를 쓴다. 개인키·대칭키가 HSM 밖으로 평문으로 나오지 않는다.
- **관련:** [[EPOS-30i]] · [[Secure Boot]] · [[마스터키]]

### Secure Boot

- **우리 용어:** Secure Boot (보안 부팅)
- 매 부팅 시 [[HSM]]이 실행 이미지의 무결성을 검증한 뒤에만 다음 단계를 실행시키는 신뢰 연쇄(HSM → FBL → App)다. EPOS-30i는 부팅 무결성에 **AES-128-CMAC**(기기별 키)을 쓴다. OTA로 배포되는 대상이 아니라 기기 내부 검증이다.
- **관련:** [[HSM]] · [[Secure Flash]]

### Secure Flash

- **우리 용어:** Secure Flash (보안 플래시)
- 새 이미지를 설치할 때 [[HSM]]이 복호화·진위검증(ECDSA)·안티롤백을 수행하며 비활성 뱅크에 기록하는 절차다. UDS `0x29` 인증을 전제로 하고 `0x34/0x36/0x37`로 데이터를 전송한다. 이미지 진위는 [[Secure Boot]]의 대칭 CMAC과 달리 **비대칭 ECDSA P-256**을 쓴다.
- **관련:** [[Secure Boot]] · [[안티롤백]] · [[SE Binary]]

### A/B Dual Bank

- **우리 용어:** A/B Dual Bank (이중 뱅크)
- 프로그램 메모리를 두 뱅크로 두고, 비활성 뱅크에 새 이미지를 기록한 뒤 스왑(`UCB_SWAP`)으로 활성화하는 구조다. 설치 실패 시 기존 활성 뱅크가 그대로 남아 무중단 복귀한다([[EPOS-10i]]의 [[Insurance Kernel]] 재플래시와 대비되는 이점).
- **관련:** [[EPOS-30i]] · [[안티롤백]]

### SE Binary

- **우리 용어:** SE Binary (Signed-Encrypted Binary)
- 보안처리 주체([[KMS]])가 원본 이미지를 **암호화 + ECDSA 서명**해 만든 결과물(이미지 헤더 포함)이다. [[eSync Server]]는 이를 의미를 해석하지 않는 **통짜 페이로드**로 취급해 [[Component / Package]]로 감싼다(2계층 보안 모델).
- **관련:** [[Secure Flash]] · [[Component / Package]]

### 마스터키

- **우리 용어:** 마스터키 (시드키) · 세대 로테이션
- 모든 EPOS-30i가 공유하는 대칭 시드키다. 릴리스별 콘텐츠 암호키([[CEK]])를 여기서 파생한다. **세대(버전)**로 구분해, 유출 시 해당 세대만 폐기하고 새 세대로 롤포워드한다. 세대 갱신은 기기 공개키로 [[ECIES]] 래핑해 전달한다. 유출돼도 진위(ECDSA)는 별도라 위조는 불가능하다(기밀성만 손실).
- **관련:** [[CEK]] · [[ECIES]] · [[HSM]]

### CEK

- **우리 용어:** CEK (Content Encryption Key) · 파생 콘텐츠키
- 컴포넌트(릴리스)별 대칭 암호키다. `CEK = KDF([[마스터키]][세대], IV‖FW_ID)`로 파생하며(SP800-108 KBKDF), 이미지 암호화(AES-128-CTR)에 쓴다. 별도 전달 없이 기기가 이미지 헤더의 IV·세대로 재파생하므로 오프라인·유선에서도 동작한다.
- **관련:** [[마스터키]] · [[Secure Flash]]

### ECIES

- **우리 용어:** ECIES (타원곡선 통합 암호화)
- 상대 공개키로 대칭키를 안전하게 전달하는 표준 기법(임시 ECDH → KDF → AES-GCM 래핑)이다. EPOS-30i 프로비저닝에서 [[마스터키]]를 기기 공개키로 래핑해 주입·갱신할 때 쓴다.
- **관련:** [[마스터키]] · [[HSM]]

### 안티롤백

- **우리 용어:** 안티롤백 (Anti-Rollback)
- 취약한 옛 버전으로의 다운그레이드를 막는 장치다. EPOS-30i는 이미지 헤더의 버전(FW Version)과 모노토닉 카운터로 기기 자체가 강제한다. [[eSync Server]] 측 manifest의 rollback 기준과 함께 이중으로 작동한다.
- **관련:** [[A/B Dual Bank]] · [[Secure Flash]]
