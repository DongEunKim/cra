# 용어집

각 사양서([10 PKI](10-PKI-사양서.md) · [20 프로비저닝](20-프로비저닝-사양서.md) · [30 eSync OTA 공통 아키텍처](30-eSync-OTA-공통아키텍처.md) · [31 EPOS-10i](31-EPOS-10i-OTA사양서.md) · [32 EPOS-30i](32-EPOS-30i-업데이트-사양서.md) · [40 유선업데이트](40-유선업데이트-사양서.md)) 본문은 표준 스택인 [eSync](#esync)의 용어를 인용하였다. 이 문서는 본 사양에서 쓰는 용어(eSync 스택 용어·시스템 구성요소·보안 개념)가 무엇을 뜻하고 어떤 구성요소에 해당하는지를 정리한다.

## 배경 개념 정리
  - **OTA(Over-The-Air)** — 장비를 정비소에 들이지 않고 무선망으로 소프트웨어를 갱신하는 방식.
  - **PKI(Public Key Infrastructure, 공개키 기반구조)** — 인증서로 신원과 서명을 증명하는 체계. 최상위 인증기관을 정점으로 하위 인증기관·최종 인증서가 계층(체인)을 이룬다. 상위의 서명을 차례로 따라가 신뢰를 확인한다.
  - **인증서(certificate)** — 공개키와 그 소유자 정보를 인증기관이 서명해 묶은 전자 신분증. 표준은 X.509.
  - **개인키/공개키** — 짝을 이루는 두 키. 개인키로 서명하면 공개키로 검증한다. 개인키는 소유자만 보관한다.
  - **mTLS(mutual TLS, 상호 인증 TLS)** — 서버와 클라이언트가 서로 상대의 인증서를 확인하는 암호화 연결.

## eSync 스택

본 사양 전체의 기반이 되는 표준 스택과 그것이 동작하는 장비 게이트웨이다.

### eSync

- Excelfore의 차량·장비용 OTA·업데이트 프레임워크(표준 스택)다. **본 사양([10](10-PKI-사양서.md)~[40](40-유선업데이트-사양서.md))은 모두 eSync 위에 정의된다.** 클라우드의 [eSync Server](#esync-server), 장비 게이트웨이([TGU](#tgu))의 [eSync Client](#esync-client)와 제어기별 [eSync Agent](#esync-agent)로 구성되며, [Component / Package](#component--package) 데이터 모델·서명·[Campaign](#campaign)·전송([AWS IoT Core](#aws-iot-core))·상태 보고 규약을 제공한다. 소프트웨어에 개발자 서명을 두지 않고 중앙([KMS](#kms))에서 서명하는 것이 본 사양의 채택 방식이다.
- **관련:** [eSync Server](#esync-server) · [eSync Client](#esync-client) · [eSync Agent](#esync-agent) · [TGU](#tgu)

### TGU

- Telematics Gateway Unit. 장비의 통신 게이트웨이 노드로, [eSync Client](#esync-client)와 제어기별 [eSync Agent](#esync-agent)가 이 노드에서 동작한다. 클라우드와 **mTLS**로 연결되는 유일한 창구이며, CAN 관점에서는 [SGW](#sgw) 뒤의 내부 노드다. 자기 [디바이스 인증서](#디바이스-인증서)로 신원을 증명한다.
- **관련:** [eSync Client](#esync-client) · [eSync Agent](#esync-agent) · [SGW](#sgw) · [디바이스 인증서](#디바이스-인증서)

## 클라우드·백엔드 시스템

배포를 지시하고, 소프트웨어를 보관·서명하며, 장비와 통신하는 서버군이다.

### eSync Server

- 업데이트를 어느 장비에 언제 배포할지 정하고(Campaign·타겟팅), 소프트웨어 구성요소와 Package를 보관하며, 배포 이력을 남기는 OTA 배포 플랫폼(클라우드 백엔드)이다. (인증서를 발급하는 인증기관은 **아님**) 소프트웨어를 내보낼 때는 [Code Sign Certificate](#cs-cert)의 개인키로 서명하는 **서명자**로, 장비가 접속할 때는 장비 인증서가 유효한지 확인하는 **검증자**로 동작한다.
- **관련:** [eSync Client](#esync-client) · [Operator UI](#operator-ui) · [GPDM](#gpdm) · [KMS](#kms)

### eSync Client

- 장비 쪽 게이트웨이 노드(TGU)에서 동작하는 오케스트레이션 구성요소다. 클라우드와 **mTLS**로 통신하며, 내려받은 업데이트를 장비 안의 여러 제어기에 설치하도록 지휘한다. 장비에서 클라우드로 나가는 단일 창구 역할을 한다.
- **관련:** [eSync Agent](#esync-agent) · [eSync Server](#esync-server)

### eSync Agent

- 실제 설치를 수행하는 구성요소로, 내려받은 소프트웨어를 대상 제어기에 전달·설치한다. **대상 제어기(노드)별로 하나씩** 있으며, [Component / Package](#component--package)의 `type`이 담당 Agent를 지정한다. 현재는 모든 Agent가 게이트웨이(TGU)에 co-locate한다. EPOS-10i처럼 스스로 서명을 검증할 능력이 없는 제어기에서는 담당 Agent가 검증을 **대행**한 뒤 평문으로 설치하고, [EPOS-30i](#epos-30i)처럼 HSM을 보유한 제어기에서는 Agent가 전달을 맡고 검증·복호화는 **제어기 HSM이 자체 수행**한다.
- **관련:** [eSync Client](#esync-client) · [CS Cert](#cs-cert)

### Operator UI

- Campaign·Package·설치 현황을 사람이 조작하는 단일 운영 콘솔이다. RBAC(Role-Based Access Control, 역할 기반 접근제어)로 권한을 나눠, 딜러·사후관리(AS) 담당자에게 필요한 기능만 부분 개방한다.
- **관련:** [eSync Server](#esync-server)

### GPDM

- HD건설기계의 PLM(제품 수명주기 관리, Product Lifecycle Management) 시스템이다. 소프트웨어와 그 부품 목록(SW BOM, Bill of Materials)을 관리한다. 배포될 소프트웨어의 원본이 시작되는 유일한 원장으로, GPDM에서 정식 릴리스된 산출물(Component 소스)만 [eSync Server](#esync-server)로 넘어간다.
- **관련:** [eSync Server](#esync-server)

### KMS

- 서명에 쓰는 개인키를 보관하는 키 관리 시스템(Key Management System)이다. 개인키는 시스템 밖으로 나오지 않는다. [eSync Server](#esync-server)가 서명이 필요하면 대상 데이터를 KMS에 보내고, KMS 내부에서 서명한 결과만 돌려받는다. 키 자체를 노출하지 않으므로 유출 위험을 낮춘다.
- **관련:** [CS Cert](#cs-cert) · [eSync Server](#esync-server)

### VLM

- 장비 레지스트리다. 장비의 시리얼 번호, 차대번호(VIN, Vehicle Identification Number), 장비 옵션 사이의 대응 관계와 소프트웨어 구성 이력(SBOM, Software Bill of Materials)을 관리한다. Campaign이 옵션별 [SW 품번](#sw-품번) 변종을 정확히 겨냥할 때 판단 근거가 된다.
- **관련:** [SW 품번](#sw-품번) · [eSync Server](#esync-server)

### AWS IoT Core

- [eSync Server](#esync-server)와 장비(TGU)를 잇는 통신 접속점이다. TGU와 **mTLS**로 연결하고, 업데이트 지시 같은 신호(잡·MQTT 메시지)를 중계한다. 통신·전송 담당 팀 소관이다.
- **관련:** [eSync Client](#esync-client) · [JITP](#jitp)

### JITP

- 장비(TGU)가 클라우드에 처음 접속하는 순간의 서버측 등록 절차(Just-In-Time Provisioning)다. [AWS IoT Core](#aws-iot-core)가 그 장비의 사물(Thing)·인증서 정보를 계정에 자동 등록·활성화한다. 인증서를 새로 **발급**하는 것이 아니라([디바이스 인증서](#디바이스-인증서)는 Tier-1 공정에서 [Device CA](#device-ca)가 이미 발급함), 이미 있는 인증서를 클라우드에 **등록**하는 과정이다.
- **관련:** [디바이스 인증서](#디바이스-인증서) · [VLM](#vlm)

## 인증기관(CA)과 신뢰 구조

누가 인증서를 발급하고, 그 신뢰가 어디서 출발하는지를 정하는 계층이다. CA는 Certificate Authority(인증기관)의 약자다.

### OEM Root CA

- PKI 전체의 최상위 인증기관이다. 이 기관의 개인키는 인터넷과 분리해(오프라인) 보관하며, 오직 하위 인증기관을 발급할 때만 사용한다. 각 제어기에 심어 두는 신뢰의 출발점([신뢰앵커](#신뢰앵커))이 여기서 나온다 — 이 앵커는 공개키가 아니라 Root CA 인증서로 배포한다. 아래의 [Device CA](#device-ca)·[Code Sign CA](#code-sign-ca)·[Diagnostic License CA](#diagnostic-license-ca)가 모두 이 기관의 자식이다.
- **관련:** [Device CA](#device-ca) · [Code Sign CA](#code-sign-ca) · [Diagnostic License CA](#diagnostic-license-ca)

### Device CA

- 장비 신원 증명서, 곧 [디바이스 인증서](#디바이스-인증서)를 발급하는 인증기관이다. [OEM Root CA](#oem-root-ca)의 하위에 있으며, 개인키는 [KMS](#kms)에 보관한다.
- **관련:** [디바이스 인증서](#디바이스-인증서) · [OEM Root CA](#oem-root-ca)

### Code Sign CA

- 소프트웨어에 서명할 자격을 증명하는 [CS Cert](#cs-cert)를 발급하는 인증기관이다. [OEM Root CA](#oem-root-ca)의 하위에 있으며, 개인키는 [KMS](#kms)에 보관한다.
- **관련:** [CS Cert](#cs-cert) · [OEM Root CA](#oem-root-ca)

### Diagnostic License CA

- 유선 진단툴([DMS](#dms))에 발급하는 [DMS License](#dms-license)를 담당하는 인증기관이다. [OEM Root CA](#oem-root-ca) 아래에서 [Device CA](#device-ca)·[Code Sign CA](#code-sign-ca)와 같은 계층의 인증기관이며, 개인키는 [KMS](#kms)에 보관한다.
- **관련:** [OEM Root CA](#oem-root-ca) · [DMS License](#dms-license)

### 신뢰앵커

- 인증서 체인 검증의 출발점이 되는 최상위 신뢰(Trust Anchor)다. **공개키만이 아니라 자기서명 CA 인증서로** 보유한다 — 경로 검증에는 앵커의 이름(DN)·제약(용도·CA 여부)이 필요하기 때문이다(RFC 5280). 디바이스는 목적별로 여러 앵커를 갖는다: 자체 PKI 검증엔 [OEM Root CA](#oem-root-ca) 인증서, AWS 전송 검증엔 [Amazon Root CA](#amazon-root-ca) 인증서.
- **관련:** [OEM Root CA](#oem-root-ca) · [Amazon Root CA](#amazon-root-ca)

### Amazon Root CA

- AWS가 운영하는 공개 루트 인증기관(Amazon Trust Services)이다. TGU가 [AWS IoT Core](#aws-iot-core) 엔드포인트에 **mTLS**로 접속할 때 **서버(엔드포인트) 인증서를 검증하는 신뢰앵커**로 쓴다. [OEM Root CA](#oem-root-ca)(OEM 자체 PKI)와는 별개이며, TGU는 둘 다 인증서로 보유한다. 코드서명·[eSync Server](#esync-server) 검증은 OEM Root CA로, AWS 엔드포인트 검증은 Amazon Root CA로 한다.
- **관련:** [AWS IoT Core](#aws-iot-core) · [신뢰앵커](#신뢰앵커) · [OEM Root CA](#oem-root-ca)

## 인증서

앞의 인증기관이 발급하는 최종 신분증들이다. 각각 증명하는 대상이 다르다.

### CS Cert

- [Code Sign CA](#code-sign-ca)가 발급한 최종(리프, leaf) 코드서명 인증서로, "이 키로 서명한 소프트웨어는 정품"임을 보증한다. 용도가 코드서명으로 한정된다(`EKU=codeSigning`, EKU는 Extended Key Usage). 짝이 되는 개인키는 [KMS](#kms)에 두고 소프트웨어 구성요소에 서명하며, 검증자(TGU 또는 제어기)가 그 서명을 검증할 수 있도록 인증서 자체는 구성요소에 함께 실어 보낸다. 유출 피해를 줄이기 위해 수명이 짧고 주기적으로 교체(회전)한다.
- **관련:** [Code Sign CA](#code-sign-ca) · [eSync Server](#esync-server)

### 디바이스 인증서

- [Device CA](#device-ca)가 발급한 최종 인증서로, 장비(제어기)의 신원을 증명한다. 시리얼 번호를 이름으로 담는다(`CN=Serial`, CN은 Common Name). **mTLS** 접속에서 [eSync Client](#esync-client)가 자신이 정품 장비임을 입증하는 데 쓴다. 부품 공정(Tier-1)에서 발급되며, 짝이 되는 개인키는 제어기 안에만 보관한다.
- **관련:** [Device CA](#device-ca) · [eSync Client](#esync-client)

### DMS License

- 유선 진단툴([DMS](#dms))에 발급하는 짧은 수명의 X.509 인증서다. 발급받은 PC의 고유 식별자와 조작자 인증을 근거로 만들며, 그 사람이 어떤 작업을 할 수 있는지를 역할 식별자(Role OID)로 담는다. 같은 인증서 하나를, 게이트웨이([SGW](#sgw))는 [UDS 0x29 APCE](#uds-0x29-apce)로, 게이트웨이 노드([eSync Client](#esync-client))는 **mTLS**로 각각 검증한다.
- **관련:** [Diagnostic License CA](#diagnostic-license-ca) · [DMS](#dms)

## 소프트웨어 구성요소·데이터

배포되는 소프트웨어 꾸러미와 그 안에 담기는 메타데이터다.

### Component / Package

- **Component**는 특정 대상 노드(`nodeName`)에 설치되는, 버전이 매겨진 소프트웨어 단위다(`name`·`type`·`versions` 등을 가지며, 바이너리 무결성은 `deltaSha`에 SHA-256 해시로 기록). **Package**는 함께 배포해야 하는 Component들을 묶은 꾸러미다(`components`·`componentRules`, 그리고 하나라도 실패하면 전부 롤백하는 `atomicRollback`). Campaign은 이 Package 단위로 배포한다.
- **관련:** [manifest.xml](#manifestxml) · [Signed Component Database](#signed-component-database)

### Component 소스

- [GPDM](#gpdm)이 [eSync Server](#esync-server)에 제공하는 릴리스 산출물(바이너리 + 메타데이터)이다. eSync Server는 이를 입력받아 서명된 [Component / Package](#component--package)로 만든다. HSM 보유 제어기의 경우 그 바이너리는 상류에서 준비된 [SE Binary](#se-binary)다. 상류 준비(서명·암호화)·제조 배포 세부는 OTA 사양 범위 밖이며 Component 소스에 캡슐화된다.
- **관련:** [GPDM](#gpdm) · [Component / Package](#component--package) · [SE Binary](#se-binary)

### manifest.xml

- Component(ZIP) 안에 들어가는 메타데이터 파일이다. 설치 대상 노드, 종류(type), 버전, 롤백 가능 여부, Delta 정보, [SW 품번](#sw-품번), [호환성 정보 (HW)](#호환성-정보-hw) 등을 담는다. Component 전체에 서명하므로, 이 매니페스트의 내용도 그 서명으로 함께 보증된다.
- **관련:** [Component / Package](#component--package) · [호환성 정보 (HW)](#호환성-정보-hw) · [SW 품번](#sw-품번)

### Signed Component Database

- [eSync Server](#esync-server)가 서명을 마친 Component를 보관하는 저장소다. 배포는 여기 담긴, 이미 서명된 산출물에서 나간다.
- **관련:** [Component / Package](#component--package)

### Delta

- 소프트웨어 전체가 아니라 기준 버전과 달라진 부분만 전송하는 갱신 방식이다. 전송량과 시간을 줄인다. Delta 정보(`manifest_diff.xml`)와 기준 버전 참조를 함께 보내면, [eSync Agent](#esync-agent)가 기준 버전에 Delta를 더해 완성 이미지를 재구성한다.
- **관련:** [manifest.xml](#manifestxml) · [Component / Package](#component--package)

### SW 품번

- 장비 옵션별 소프트웨어 변종을 구별하는 **식별자**(Part Number)다. [manifest.xml](#manifestxml)에 담기지만, 이것으로 설치 가능 여부를 판정하지는 않는다(그 판정은 [호환성 정보 (HW)](#호환성-정보-hw)가 맡는다). 어느 장비에 어느 품번을 적용할지는 [VLM](#vlm)과 정책으로 정하며, 장비가 스스로 골라 맞추지 않는다.
- **관련:** [VLM](#vlm) · [호환성 정보 (HW)](#호환성-정보-hw)

### 호환성 정보 (HW)

- 해당 펌웨어를 설치할 수 있는 하드웨어 형상(모델·버전)을 명시한 정보다. [manifest.xml](#manifestxml)에 담기며, [eSync Agent](#esync-agent)가 진단 명령(UDS `0x22`)으로 제어기에서 실제 하드웨어 값을 읽어 이 명시값과 대조해 설치 가능 여부를 판정한다.
- **관련:** [manifest.xml](#manifestxml) · [SW 품번](#sw-품번)

## 진단·유선 경로

무선(OTA)이 아니라 정비 현장에서 케이블로 장비에 접속하는 경로와, 그 통신에 쓰는 진단 규약이다.

### DMS

- 장비를 진단하고 소프트웨어를 유선으로 설치하는 Windows PC 프로그램(C#)이다(DMS, Diagnostic Monitoring System). 장비에 상주하는 [eSync Client](#esync-client)·[eSync Agent](#esync-agent)가 없는 대신, 서명과 호환성을 스스로 검증한 뒤 [OBD-II](#obd-ii) 단자로 직접 설치하는 **유선 설치자**다(역할은 TGU와 유사). 설치할 서명 Component·Package는 [eSync Server](#esync-server)/대시보드에서 내려받는다.
- **관련:** [DMS License](#dms-license) · [SGW](#sgw) · [OBD-II](#obd-ii)

### SGW

- 장비 안에서 외부 진단 단자([OBD-II](#obd-ii)) 쪽 CAN 통신을 내부망과 분리·보호하는 보안 게이트웨이(Secure Gateway)다. 자체 보안 연산 장치([HSM](#hsm))를 갖는다. 유선 진단툴이 접속하면 그 [DMS License](#dms-license)를 [UDS 0x29 APCE](#uds-0x29-apce)로 검증하고, 통과한 경우에만 특정 CAN 선로를 개방한다. 신원·신뢰앵커를 미리 주입해 두는 프로비저닝 대상이다.
- **관련:** [DMS](#dms) · [UDS 0x29 APCE](#uds-0x29-apce) · [진단전용 CAN](#진단전용-can-private-can)

### 진단전용 CAN (Private CAN)

- [SGW](#sgw)와 특정 제어기 사이에 진단·플래시 목적으로만 구성하는 별도 CAN 선로다. [DMS License](#dms-license) 기반 [UDS 0x29 APCE](#uds-0x29-apce) 인증을 수행하지 못하는 외부 진단툴을 수용해야 할 때 쓴다. SGW가 제어기 Flashing에 필요한 UDS CAN ID를 등록해 두고, 외부 진단툴의 접근을 해당 CAN ID만 필터링하여 이 선로로 라우팅함으로써 외부 경계를 통제한다(엔진 제어기 유선 케이스 2, [33 §4.2](33-ECU-OTA사양서.md)).
- **관련:** [SGW](#sgw) · [OBD-II](#obd-ii)

### OBD-II

- 장비 외부에 노출된 표준 진단 접속 단자다. CAN([SGW](#sgw) 경유)과 이더넷([eSync Client](#esync-client) 경유) 두 경로의 접속을 제공한다.
- **관련:** [SGW](#sgw) · [DMS](#dms)

### UDS 서비스

- 제어기를 진단·정비하기 위한 표준 통신 규약(UDS, Unified Diagnostic Services; ISO 14229)이다. 서비스는 기능별 번호로 구분한다. `0x22`(ReadDataByIdentifier — 하드웨어 ID 조회), `0x27`(SecurityAccess — 시드·키 교환으로 플래시 세션을 여는 관문), `0x34`/`0x36`/`0x37`(RequestDownload/TransferData/RequestTransferExit — 플래시 데이터 전송), `0x29`(Authentication — 인증서 기반 인증, [SGW](#sgw)가 [DMS License](#dms-license) 검증에 사용). `0x29`는 암호 연산이 불가능한 [EPOS-10i](#epos-10i)에는 쓰지 않고, [HSM](#hsm)을 보유한 [EPOS-30i](#epos-30i)가 [Secure Flash](#secure-flash) 세션 관문으로 쓴다.
- **관련:** [eSync Agent](#esync-agent) · [UDS 0x29 APCE](#uds-0x29-apce)

### UDS 0x29 APCE

- [UDS 서비스](#uds-서비스) 중 `0x29`(Authentication)의 인증서 기반(PKI) 방식이다(ISO 14229:2020). APCE는 그 인증 흐름의 명칭이다. 순서는 인증서 제시 → 체인 검증 → 서버가 보낸 도전값(challenge)에 개인키로 서명 → 개인키 소유 증명 → 역할(role) 기반 권한 부여로 이어진다. [SGW](#sgw)가 유선 진단툴([DMS](#dms))을 검증하는 방식이다.
- **관련:** [SGW](#sgw) · [DMS License](#dms-license)

### DoIP

- 진단 통신(UDS)을 이더넷·IP망 위로 실어 나르는 전송 표준(Diagnostics over IP; ISO 13400)이다. 진단 메시지가 흐르기 전에 게이트웨이가 접속을 통제하는 [routing activation](#routing-activation)과 논리주소 라우팅을 제공하지만, 인증 자체는 상위 계층에 맡긴다. TGU는 DoIP를 쓰지 않으므로, 접근제어를 **mTLS**로 대신한다.
- **관련:** [eSync Client](#esync-client)

### routing activation

- [DoIP](#doip)에서 진단 메시지가 오가기 전에, 게이트웨이가 접속한 클라이언트의 자격을 확인하고 내부 경로를 열어 주는 관문 절차다. DoIP를 쓰지 않는 TGU는 이 역할을 **mTLS**와 역할 기반 접근제어로 대체한다.
- **관련:** [DoIP](#doip)

## 정책·운영 개념

설치 시점·복구·시각처럼 절차를 통제하는 개념들이다.

### Insurance Kernel

- 제어기의 보호된 메모리 영역에 상주하는 최소한의 복구 코드(복구 부트로더)다. 플래시 도중 문제가 생겨 애플리케이션이 손상되더라도, 이 코드가 남아 있어 다시 플래시해 장비를 복구할 수 있다. 메모리 뱅크가 하나뿐이라 안전한 예비 영역이 없는(싱글뱅크) 제어기의 복구 수단이다.
- **관련:** [eSync Agent](#esync-agent)

### 설치 정책

- 업데이트를 언제·어떤 조건에서 설치할지 통제하는 규칙(InstallationPolicy)이다. 시동이 꺼진 상태(`ignition_off`), 네트워크 상태, 허용 시간대 같은 조건을 지정해, 안전하지 않은 시점의 설치를 막는다.
- **관련:** [eSync Client](#esync-client)

### 신뢰 시각

- 인증서 유효기간이나 폐기 여부(OCSP) 확인처럼, 신뢰할 수 있는 현재 시각(Trusted Time)을 필요로 하는 검증에 쓰는 시각원이다. 장비가 임의로 조작할 수 없는 믿을 만한 출처를 TGU가 확보해야 한다.
- **관련:** [디바이스 인증서](#디바이스-인증서)

### Campaign

- 어느 장비군에 어떤 [Component / Package](#component--package)를 언제 배포할지 정하는 배포 단위다. 차량(장비) 단위로 대상을 선정(VIN·그룹)하며 단계적 롤아웃·중단(halt)을 지원한다. [VLM](#vlm)·정책과 연동해 옵션별 [SW 품번](#sw-품번) 변종을 겨냥한다.
- **관련:** [eSync Server](#esync-server) · [VLM](#vlm)

### EOL

- End-of-Line. 제조 생산라인의 종단 공정으로, 제어기에 키·인증서·신뢰앵커를 주입(프로비저닝)하는 시점이다. EPOS-30i의 [HSM](#hsm) 키 슬롯·[마스터키](#마스터키) 주입이 이 단계에서 이뤄진다.
- **관련:** [Tier-1](#tier-1) · [HSM](#hsm)

### Tier-1

- 완성차·장비 제조사에 부품을 공급하는 1차 부품 공정(공급사)이다. 제어기의 [디바이스 인증서](#디바이스-인증서)·신뢰앵커 등 초기 신원·자격이 이 공정에서 주입된다.
- **관련:** [디바이스 인증서](#디바이스-인증서) · [EOL](#eol)

### CRA

- EU 사이버 복원력 법안(Cyber Resilience Act, Regulation (EU) 2024/2847). 디지털 요소 제품의 보안 요구(보안 업데이트·취약점 관리·SBOM·추적성 등)를 규정한다. [EPOS-30i](#epos-30i) 등 본 사양의 보안 강화가 대응하는 규제다.
- **관련:** [EPOS-30i](#epos-30i)

## 암호 알고리즘·기법

서명·암호화·해시에 쓰는 표준 알고리즘이다. 배경 개념(인증서·개인키/공개키)은 [읽는 법](#읽는-법)에 있다.

### ECDSA

- 타원곡선 디지털 서명 알고리즘(Elliptic Curve DSA)이다. 곡선 [P-256](#p-256)·해시 [SHA-256](#sha-256)으로 코드서명([CS Cert](#cs-cert))·이미지 진위([Secure Flash](#secure-flash))·UDS 인증([UDS 0x29 APCE](#uds-0x29-apce))에 쓴다. 개인키로 서명, 공개키로 검증하는 비대칭 방식이라 검증자는 위조할 수 없다.
- **관련:** [P-256](#p-256) · [SHA-256](#sha-256) · [CS Cert](#cs-cert)

### P-256

- NIST 표준 타원곡선 secp256r1이다. 본 사양의 [ECDSA](#ecdsa) 서명과 [ECIES](#ecies) 키 전달에 쓰는 곡선이다.
- **관련:** [ECDSA](#ecdsa) · [ECIES](#ecies)

### AES-128

- 128비트 대칭키 블록 암호다. **CTR 모드**는 펌웨어 기밀성(이미지 암호화, [CEK](#cek))에, **CMAC**은 무결성 태그([Secure Boot](#secure-boot) 부팅 무결성)에 쓴다. 대칭키라 검증자와 생성자가 같으므로, 이미지 진위는 별도로 [ECDSA](#ecdsa)가 담당한다.
- **관련:** [CEK](#cek) · [Secure Boot](#secure-boot)

### SHA-256

- 256비트 암호 해시다. 서명 대상 요약(digest) 생성과 무결성 비교에 쓴다.
- **관련:** [ECDSA](#ecdsa)

### KDF·IV

- **KDF**(Key Derivation Function)는 상위 키에서 하위 키를 파생하는 함수다. 본 사양은 SP800-108 KBKDF로 [마스터키](#마스터키)에서 [CEK](#cek)를 파생한다. **IV**(Initialization Vector)는 AES-CTR 암호화의 난수 초기값으로, 이미지 헤더에 실려 기기가 CEK를 재파생하는 입력이 된다.
- **관련:** [CEK](#cek) · [마스터키](#마스터키)

## 표준·프로토콜 약어

PKI·진단·통신·규제에서 쓰는 표준 약어다.

### OCSP

- Online Certificate Status Protocol. 인증서가 폐기됐는지 온라인으로 확인하는 프로토콜이다. TGU↔클라우드 온라인 경계에서 [신뢰 시각](#신뢰-시각) 하에 폐기를 확인한다(오프라인 경계는 [CRL](#crl) 등으로 보완).
- **관련:** [CRL](#crl) · [신뢰 시각](#신뢰-시각)

### CRL

- Certificate Revocation List. 폐기된 인증서 목록이다. 온라인 확인([OCSP](#ocsp))이 어려운 오프라인 경계(유선·현장)에서 사전 배포해 폐기를 강제한다.
- **관련:** [OCSP](#ocsp) · [DMS License](#dms-license)

### OID

- Object Identifier. 표준·확장 항목을 전역 유일하게 가리키는 식별자다. 인증서 용도(EKU)나 [DMS License](#dms-license)의 역할(Role OID) 표기에 쓴다.
- **관련:** [DMS License](#dms-license)

### NRC

- Negative Response Code. [UDS 서비스](#uds-서비스) 요청이 거부될 때 반환하는 부정 응답 코드다. 예: `0x33`(securityAccessDenied), `0x34`(authenticationRequired).
- **관련:** [UDS 서비스](#uds-서비스) · [UDS 0x29 APCE](#uds-0x29-apce)

### SecOC

- Secure Onboard Communication. CAN 등 차량 내부 통신 메시지의 무결성·신선도를 MAC으로 보호하는 표준(AUTOSAR)이다. 현재 내부 CAN에는 미적용이라, 그 잔여 위험을 게이트웨이·세션 게이트로 보완한다([40 §5](40-유선업데이트-사양서.md)).
- **관련:** [SGW](#sgw)

### SBOM

- Software Bill of Materials. 소프트웨어를 구성하는 부품·의존성 목록이다. 취약점 추적·[CRA](#cra) 대응의 근거가 되며 [VLM](#vlm)이 장비별 구성 이력으로 관리한다.
- **관련:** [VLM](#vlm) · [CRA](#cra)

### MQTT

- 경량 발행/구독 메시징 프로토콜이다. TGU와 [AWS IoT Core](#aws-iot-core) 사이의 시그널링(업데이트 잡·상태)을 나르는 데 쓴다.
- **관련:** [AWS IoT Core](#aws-iot-core)

## 제어기·HSM 보안 (EPOS 계열)

HSM을 보유한 제어기가 스스로 서명 검증·복호화·Secure Boot를 수행할 때 쓰는 개념들이다.

### EPOS-10i

- 유압 제어기(현세대)다. HSM이 없어 서명 검증·암복호화를 스스로 못 하고, 메모리 뱅크가 하나(싱글뱅크)이며 UDS `0x29`를 지원하지 않는다. 무결성 검증을 [eSync Agent](#esync-agent)(TGU)가 대행하고, 평문으로 플래시하며, `0x27`로 세션을 보호한다. 상세는 [31 EPOS-10i](31-EPOS-10i-OTA사양서.md).
- **관련:** [eSync Agent](#esync-agent) · [Insurance Kernel](#insurance-kernel) · [EPOS-30i](#epos-30i)

### EPOS-30i

- EPOS-10i를 CRA에 대응해 업그레이드한 차세대 유압 제어기로, [HSM](#hsm)과 [A/B Dual Bank](#ab-dual-bank)를 갖춘다. 서명 검증·복호화를 **제어기 자체가** 수행하고, 암호화 페이로드([Secure Flash](#secure-flash))를 받으며, UDS `0x29`로 세션을 보호한다. 상세는 [32 EPOS-30i](32-EPOS-30i-업데이트-사양서.md).
- **관련:** [HSM](#hsm) · [Secure Boot](#secure-boot) · [Secure Flash](#secure-flash) · [A/B Dual Bank](#ab-dual-bank)

### HSM

- 제어기 안에서 키를 보관하고 암호 연산(서명 검증·복호화·MAC)을 전담하는 하드웨어 보안 모듈(Hardware Security Module)이다. EPOS-30i는 AURIX TC387QP의 HSM 코어(Cortex-M3)를 쓴다. 개인키·대칭키가 HSM 밖으로 평문으로 나오지 않는다.
- **관련:** [EPOS-30i](#epos-30i) · [Secure Boot](#secure-boot) · [마스터키](#마스터키)

### Secure Boot

- 매 부팅 시 [HSM](#hsm)이 실행 이미지의 무결성을 검증한 뒤에만 다음 단계를 실행시키는 신뢰 연쇄(HSM → FBL → App)다. EPOS-30i는 부팅 무결성에 **AES-128-CMAC**(기기별 키)을 쓴다. OTA로 배포되는 대상이 아니라 기기 내부 검증이다.
- **관련:** [HSM](#hsm) · [Secure Flash](#secure-flash)

### FBL

- Flash Bootloader. 제어기의 플래시 갱신을 담당하는 부트로더다. EPOS-30i의 [Secure Boot](#secure-boot) 신뢰 연쇄(HSM → FBL → App)에서 [HSM](#hsm)이 검증한 뒤 실행되며, App 이미지 검증과 [A/B Dual Bank](#ab-dual-bank) 스왑을 수행한다.
- **관련:** [Secure Boot](#secure-boot) · [A/B Dual Bank](#ab-dual-bank)

### Secure Flash

- 새 이미지를 설치할 때 [HSM](#hsm)이 복호화·진위검증(ECDSA)·안티롤백을 수행하며 비활성 뱅크에 기록하는 절차다. UDS `0x29` 인증을 전제로 하고 `0x34/0x36/0x37`로 데이터를 전송한다. 이미지 진위는 [Secure Boot](#secure-boot)의 대칭 CMAC과 달리 **비대칭 ECDSA P-256**을 쓴다.
- **관련:** [Secure Boot](#secure-boot) · [안티롤백](#안티롤백) · [SE Binary](#se-binary)

### A/B Dual Bank

- 프로그램 메모리를 두 뱅크로 두고, 비활성 뱅크에 새 이미지를 기록한 뒤 스왑(`UCB_SWAP`)으로 활성화하는 구조다. 설치 실패 시 기존 활성 뱅크가 그대로 남아 무중단 복귀한다([EPOS-10i](#epos-10i)의 [Insurance Kernel](#insurance-kernel) 재플래시와 대비되는 이점).
- **관련:** [EPOS-30i](#epos-30i) · [안티롤백](#안티롤백)

### SE Binary

- 보안처리 주체([KMS](#kms))가 원본 이미지를 **암호화 + ECDSA 서명**해 만든 결과물(이미지 헤더 포함, Signed-Encrypted Binary)이다. [eSync Server](#esync-server)는 이를 의미를 해석하지 않는 **불투명(opaque) 페이로드**로 취급해 [Component / Package](#component--package)로 감싼다(2계층 보안 모델).
- **관련:** [Secure Flash](#secure-flash) · [Component / Package](#component--package)

### 마스터키

- 모든 EPOS-30i가 공유하는 대칭 시드키(마스터키)다. 릴리스별 콘텐츠 암호키([CEK](#cek))를 여기서 파생한다. **세대**(버전)로 구분해, 유출 시 해당 세대만 폐기하고 새 세대로 롤포워드한다. 세대 갱신은 기기 공개키로 [ECIES](#ecies) 래핑해 전달한다. 유출돼도 진위(ECDSA)는 별도라 위조는 불가능하다(기밀성만 손실).
- **관련:** [CEK](#cek) · [ECIES](#ecies) · [HSM](#hsm)

### CEK

- Component(릴리스)별 콘텐츠 암호키(Content Encryption Key)다. `CEK = KDF([마스터키](#마스터키)[세대], IV‖FW_ID)`로 파생하며(SP800-108 KBKDF), 이미지 암호화(AES-128-CTR)에 쓴다. 별도 전달 없이 기기가 이미지 헤더의 IV·세대로 재파생하므로 오프라인·유선에서도 동작한다.
- **관련:** [마스터키](#마스터키) · [Secure Flash](#secure-flash)

### ECIES

- 상대 공개키로 대칭키를 안전하게 전달하는 표준 기법(ECIES, 타원곡선 통합 암호화; 임시 ECDH → KDF → AES-GCM 래핑)이다. EPOS-30i 프로비저닝에서 [마스터키](#마스터키)를 기기 공개키로 래핑해 주입·갱신할 때 쓴다.
- **관련:** [마스터키](#마스터키) · [HSM](#hsm)

### 안티롤백

- 취약한 옛 버전으로의 다운그레이드를 막는 장치(Anti-Rollback)다. EPOS-30i는 이미지 헤더의 버전(FW Version)과 모노토닉 카운터로 기기 자체가 강제한다. [eSync Server](#esync-server) 측 manifest의 롤백 기준과 함께 이중으로 작동한다.
- **관련:** [A/B Dual Bank](#ab-dual-bank) · [Secure Flash](#secure-flash)
