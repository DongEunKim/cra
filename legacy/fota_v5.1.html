차세대 제어기 소프트웨어 업데이트 보안 아키텍처 명세서

문서 버전: v5.1
문서 분류: 보안 아키텍처 / 기술 명세서
적용 대상: 배포 서버(eSync 등 연동), 인스톨러(TGU 중심), 타겟 제어기(EPOS 등)

목차

  1. FW 업데이트 패키지 전자서명 PKI
  2. FW 업데이트 패키지 구성트리 (평문 vs 암호화)
  3. 패키지 검증 주체 및 검증 절차

1. FW 업데이트 패키지 전자서명 PKI

본 장은 펌웨어(FW) 패키지의 출처 보증(Authenticity)과 무결성(Integrity)을 확보하기 위한 공개키 기반 구조(PKI) 및 전자서명 정책을 정의한다.

1.1 PKI 계층 구조 및 인증기관(CA) 분리

단일 Root CA 산하에 목적별로 중간 인증기관(Intermediate CA)을 분리하여, 권한 탈취 시 피해 범위를 격리한다.

  • OEM Root CA: 최상위 인증기관. 오프라인에 보관되며, 하위 Intermediate CA 발급 시에만 사용된다.
  • Dev-IC (Device CA): 기기 인증망. 제어기(SGW, TGU, EPOS)의 신분 증명용 고유 인증서를 발급한다.
  • CS-IC (Code Signing CA): 코드 서명망. SW 개발자 인증서를 서명 발급하며, 배포 서버를 통해 유통되는 패키지의 배포 서명을 직접 담당한다.

1.2 이중 전자서명 (Dual Signature) 아키텍처

FW 업데이트 패키지는 배포와 설치 과정의 주체별 역할에 맞추어 배포 계층(Distribution)과 설치 계층(Installation)으로 분리된 이중 전자서명 구조를 갖는다.

구분 배포 서명 (Distribution Signature) 펌웨어 서명 (Firmware Signature)
서명 주체 배포 서버 (CS-IC 개인키) 제어기 S/W 개발 주체 (SW 개발자/벤더 개인키)
보증 내용 공인된 배포 서버를 통한 배포 승인 및 설치 패키지의 신뢰성/무결성 보증 이 펌웨어가 인가된 S/W 개발자가 작성한 원본 정품임 (개발자 출처 보증)
검증 주체 인스톨러 (TGU) 타겟 제어기 (HSM 보유 시)
검증 효과 비정상/변조된 패키지의 네트워크 진입 차단 및 타겟 장비(HW ID) 오설치 방지 가짜 펌웨어의 ROM 기록 방지 및 Secure Boot 인가

2. FW 업데이트 패키지 구성트리

* 배포 서버와 OTA 서버의 관계: 배포 서버는 eSync OTA 서버를 포함하거나 이와 긴밀히 연동되어 구성된다. eSync 서버가 배포 캠페인(타겟팅, 릴리즈)을 총괄 관리하며, 펌웨어 패키징 시 배포 서명을 부착하여 인스톨러(TGU 등)로 전달하는 역할을 수행한다.

2.1 [Type A] 일반 평문 배포 트리 (암호화 미적용)

레거시 제어기나 암호화가 불필요한 제어기를 위한 표준 패키지 트리이다.

📦 FW 업데이트 패키지 (배포 서버 배포본) │ ├── 📂 [1] 배포 패키지 (Distribution Package) │ │ * 목적: 인스톨러(TGU)의 타겟 라우팅 및 설치 패키 신뢰성 검증 │ │ │ ├── 📜 CS-IC 인증서 (.der) │ │ │ ├── 📄 배포 매니페스트 (Distribution Manifest) │ │ ├── 🎯 타겟팅 메타데이터 (Target HW ID, 연식 조건, 강제 설치 플래그) │ │ ├── ⚙️ 암호화 명세 (Encryption Mode: 'NONE') │ │ └── 🔗 설치 패키지 해시 ([2]번 '설치 패키지' 덩어리에 대한 SHA-256) │ │ │ └── 🔐 배포 서명 (Distribution Signature) │ └── 📂 [2] 설치 패키지 (Installation Package) │ * 목적: 타겟 제어기의 최종 무결성 검증 및 설치 │ ├── 📜 SW 개발자 인증서 (.der) │ * 목적: 펌웨어 서명을 검증할 수 있는 공개키 제공 (CS-IC 개인키로 서명됨) │ * 예외: 타겟 제어기 ROM에 개발자 공개키가 이미 내장된 경우 생략 가능 │ ├── 📄 설치 매니페스트 (Installation Manifest) │ ├── 🔢 버전 메타데이터 (SW Version, Anti-Rollback Counter) │ └── 🔗 원본 펌웨어 해시 (아래 '순수 펌웨어'에 대한 SHA-256) │ ├── 🔐 펌웨어 서명 (Firmware Signature) │ └── 📦 펌웨어 바이너리 페이로드 └── 📄 순수 펌웨어 원본 파일 (.bin) (평문 상태)

2.2 [Type B] Secure Flash 암호화 배포 트리

고도화된 하드웨어(HSM)를 보유하여 지적재산권(기밀성) 보호가 필요한 제어기용 트리이다.

📦 FW 업데이트 패키지 (Secure Flash 2.0 적용 배포본) │ ├── 📂 [1] 배포 패키지 (Distribution Package) │ ├── 📜 CS-IC 인증서 (.der) │ ├── 📄 배포 매니페스트 (Distribution Manifest) │ │ ├── 🎯 타겟팅 메타데이터 (Target HW ID 등) │ │ ├── ⚙️ 암호화 명세 (Encryption Mode: 'AES-256-GCM') │ │ ├── 🔒 암호화된 임시 세션 키 (Encrypted TSK) │ │ │ * FW를 암호화한 대칭키(AES-TSK)를 대칭키인 **'SW-Group-Key'**로 랩핑함 │ │ └── 🔗 설치 패키지 해시 │ └── 🔐 배포 서명 (Distribution Signature) │ └── 📂 [2] 설치 패키지 (Installation Package) ├── 📜 SW 개발자 인증서 (.der) (생략 가능) ├── 📄 설치 매니페스트 (버전 및 평문 원본 해시) ├── 🔐 펌웨어 서명 (Firmware Signature) │ └── 📦 암호화된 펌웨어 바이너리 페이로드 └── 📄 순수 펌웨어 원본 파일 (.bin) * 보안: 임시 세션 키(AES-TSK)로 고속 암호화 처리됨

3. 패키지 검증 주체 및 검증 절차

본 장은 인스톨러(TGU 중심)가 패키지를 수신하여 타겟 제어기에 플래싱하기까지의 2단계 검증 시퀀스를 정의한다.

[그림 1] 배포 패키지 및 펌웨어 검증 시퀀스 다이어그램

3.1 1단계: 배포 패키지 검증 (인스톨러 역할)

  • 검증 주체: 인스톨러 (TGU)
  • 검증 수단: TGU 내부에 사전 주입된 OEM Root CA 공개키
  • 검증 절차:
    1. 패키지에 동봉된 CS-IC 인증서를 Root CA 공개키로 검증하여 배포 서버의 신원을 확인한다.
    2. 확인된 CS-IC 공개키를 사용하여 배포 서명을 검증하고, 매니페스트의 무결성을 확인한다.
    3. 배포 매니페스트 내의 설치 패키지 해시값을 직접 계산하여 알맹이(설치 패키지)가 변조되지 않았음을 확인한다.
    4. 매니페스트의 Target HW ID가 연결된 장비와 일치하는지 확인한다.
    5. 검증 완료 후 [1] 배포 패키지 껍질을 폐기하고, [2] 설치 패키지를 타겟 제어기로 전송한다.

3.2 2단계: 설치 패키지 (펌웨어) 검증

  • 검증 주체: 타겟 제어기 (HSM)
  • 검증 수단: 타겟 제어기 롬에 내장된 OEM Root CA 공개키 (또는 사전 주입된 CS-IC 공개키)
  • 검증 절차:
    1. 인스톨러로부터 설치 패키지를 수신하고, 암호화된 경우 내장된 대칭키(SW-Group-Key)로 TSK를 풀어 펌웨어를 복호화한다.
    2. 동봉된 SW 개발자 인증서를 내장된 Root CA(또는 CS-IC) 공개키로 검증한다. (인증서가 생략된 경우 내장된 키를 바로 사용)
    3. 추출한 SW 개발자 공개키로 펌웨어 서명을 검증한다.
    4. 매니페스트의 버전을 확인해 롤백 시도를 차단하고, 펌웨어를 플래시 메모리(비활성 뱅크)에 기록한다.

4. 대칭키(Group-Key) 기반 FW 암호화 (Secure Flash)

펌웨어의 기밀성을 보호하면서도, 복잡한 비대칭 연산을 줄이고 대규모 배포 스케일링을 만족하기 위해 대칭키 기반의 'SW-Group-Key' 구조를 도입한다.

[그림 2] CSR 기반 대칭키(SW-Group-Key) 인증서 매립 주입 시퀀스

4.1 인증서 확장 필드(Extension) 기반의 대칭키 주입 절차

  1. [부품사 영역] 고유 키쌍 생성 및 CSR 발급: 제어기(HSM) 최초 전원 인가 시 난수를 발생하여 디바이스 고유 키쌍(Dev-Pub/Priv)을 스스로 생성한다. 공개키(Dev-Pub)를 포함한 CSR 규격을 만들어 Tier-1 테스터로 전달한다.
  2. [OEM 영역] CSR 전송 및 KMS 연동: 테스터는 VPN을 통해 CSR을 OEM의 Dev-IC로 전송한다. Dev-IC는 내부망에 격리된 KMS에 대칭키 SW-Group-Key를 요청하고, 이를 CSR 내의 Dev-Pub으로 비대칭 암호화 받는다.
  3. [OEM 영역] X.509 확장 필드 매립: Dev-IC는 디바이스 인증서를 발급할 때, 암호문을 X.509 v3 Custom Extension 영역에 매립하여 서명한 뒤 테스터로 반환한다.
  4. [부품사 영역] 로컬 인증서 파싱 및 복호화: 테스터가 인증서를 제어기에 주입하면, 제어기는 확장 필드 안의 암호문을 자신의 Dev-Priv로 풀고 최종 대칭키인 SW-Group-Key를 HSM에 영구 저장한다.

4.2 FOTA 배포 서버의 암호화 프로세스

  1. [펌웨어 암호화]: 배포 서버는 일회용 임시 세션 키(AES-TSK)를 생성하여 펌웨어를 고속 암호화한다.
  2. [TSK 랩핑]: 배포 서버는 펌웨어를 풀 수 있는 열쇠인 AES-TSK를 대칭키인 SW-Group-Key로 암호화(Wrapping)하여 배포 매니페스트에 동봉한다.
  3. [로컬 복호화]: 타겟 제어기는 자신의 HSM에 내장된 SW-Group-Key로 AES-TSK를 복호화하고, 이를 이용해 최종 펌웨어를 복호화한다.

5. Secure Boot 및 공정 초기 주입(Factory Flashing)

부품사 양산 단계에서의 물리적 펌웨어 굽기(Factory Flashing)와, 플래싱 완료 후 기기가 부팅될 때 동작하는 로컬 무결성 검증(Secure Boot) 프로세스이다.

[참고] 활성 뱅크(Active Bank)와 HSM의 역할 분리
OTA를 지원하는 제어기는 플래시 메모리가 A/B 두 개의 뱅크(구역)로 나뉩니다. '활성 뱅크'는 수십 MB의 펌웨어 본체가 저장되어 현재 실행되고 있는 거대한 저장 창고입니다. 반면 HSM은 내부 메모리가 수 KB에 불과한 초고속 보안 계산기입니다. 부트로더는 활성 뱅크의 펌웨어를 통째로 HSM에 넣는 것이 아니라, 빠른 해시 알고리즘(SHA-256)으로 요약본(Hash)을 만든 뒤 그 작은 요약본과 서명값만 HSM으로 보내어 검증(Verify)을 위임합니다.

5.1 양산 라인의 초기 펌웨어 주입 (Factory Flashing)

부품사(Tier-1)의 양산 조립 공정에서는 FOTA 배포 패키지 구조(매니페스트, 암호화 봉투 등)를 사용하지 않으며, 물리적 케이블을 통한 다이렉트 플래싱을 수행한다.

  • 양산용 롬 이미지(Production Image): OEM은 FOTA 포장 전 단계인 [순수 펌웨어 + 펌웨어 서명(헤더) + Root CA 공개키]가 하나로 결합된 통짜 바이너리 파일(.hex/.bin)을 부품사에 제공한다.
  • 고속 굽기: 부품사 라인의 플래셔(Flasher) 장비는 JTAG, SWD 등의 하드웨어 인터페이스를 통해 롬 이미지를 플래시 메모리(활성 뱅크)에 다이렉트로 기록한다.
  • 초기 검증 앵커 확립: 이 과정을 통해 제어기는 첫 시동 전부터 내부에 'Root CA 공개키(검증 잣대)'와 헤더의 '펌웨어 서명'을 보유하게 되어, 별도의 FOTA 통신 없이도 즉각적인 Secure Boot가 가능해진다.

5.2 안티 롤백 (Anti-Rollback)

매니페스트 및 펌웨어 헤더에 기재된 보안 버전 번호(ARVN)를 하드웨어(HSM 비휘발성 카운터)와 대조하여, 취약점이 존재하는 구버전으로의 다운그레이드 공격을 하드웨어 레벨에서 원천 차단한다.

5.3 Secure Boot (안전한 부팅)

초기 양산 주입 또는 FOTA 업데이트가 완료된 후, 제어기에 전원이 인가(Ignition On)될 때마다 부트로더가 수행하는 프로세스이다.

  1. 제어기 하드웨어 부트로더가 제어권을 갖는다.
  2. 부트로더가 활성 뱅크(Active Bank) 전체를 스캔하여 펌웨어의 해시(Hash)값을 계산한다.
  3. 부트로더는 계산된 해시값과 펌웨어 헤더에 부착된 펌웨어 서명을 HSM으로 전달한다.
  4. HSM은 롬에 저장된 SW 개발자 공개키(또는 Root CA 기반 체인)를 사용하여 해당 서명을 수 밀리초(ms) 이내에 초고속 재검증한다.
  5. 무결성이 확인된 경우에만 어플리케이션 영역으로 점프하여 제어 코드를 실행하며, 검증 실패 시 정상 뱅크로의 복구(Fallback) 또는 안전 모드(Safe Mode)로 진입한다.
